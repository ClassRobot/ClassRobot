# 角色说明

## 文档目标

本文档用于说明 ClassRobot 当前代码中的角色模型、角色关系、权限入口和已知限制，便于后续做功能开发、权限治理、领域重构和 MCP 对外开放。

当前文档主要基于以下实现整理：

- `utils/roles/__init__.py`
- `utils/roles/system.py`
- `utils/models/models.py`
- `utils/helper/schema.py`
- 各命令模块中的 `__helpers__`

## 角色模型总览

当前项目里的“角色”不是单一概念，而是三层并存：

1. 平台账户层角色
2. 业务身份层角色
3. 组织内岗位层角色

这三层共同决定一个用户能看到哪些命令、能执行哪些行为、在什么范围内生效。

除此之外，系统还存在一层非常重要但不应与“角色”混淆的概念：

- 组织与层级结构

角色解决的是“你是谁、你拥有什么权限”，组织结构解决的是“你属于哪个学校、学院、专业、班级、组织，以及你的权限在哪个范围内生效”。

## 组织与层级关系

根据当前项目语义和后续目标，推荐将系统中的核心结构理解为：

- 学校
- 学院
- 专业
- 班级
- 组织
- 学生
- 教师

其中班级和组织都属于学校域中的组织单元，但它们的业务语义不同：

- 班级是稳定的教学组织单元
- 组织是更灵活的协作或治理单元

## 目标层级关系

建议后续以以下关系作为统一领域模型基线：

1. 一个学校包含多个学院
2. 一个学院包含多个专业
3. 一个专业包含多个班级
4. 一个班级包含多个学生
5. 一个学生只属于一个班级
6. 一个学生可以加入多个组织
7. 一个教师可以关联多个班级
8. 一个班级可以关联多个教师
9. 一个组织可以包含学生和教师
10. 一个组织不能包含普通用户
11. 班级和组织都应归属于学校

如果把它写成更紧凑的结构，可以理解为：

- `School -> College -> Major -> Classes -> Students`
- `School -> Organizations -> Members(Students | Teachers)`
- `Teacher <-> Classes`
- `Student -> Classes`
- `Student <-> Organizations`
- `Teacher <-> Organizations`

## 班级与组织的区别

### 班级

班级是带有稳定归属关系的教学组织单元，具有以下特征：

- 归属于学校和更细的院系结构
- 是学生的主归属单元
- 学生通常只能拥有一个班级归属
- 可承载教学、作业、请假、通知等业务
- 可关联多个教师

### 组织

组织是非班级的协作单元或治理单元，具有以下特征：

- 同样归属于学校域
- 更适合承载兴趣组、治理组、协同组、临时工作组等结构
- 成员可以是学生，也可以是教师
- 普通用户不能直接成为组织成员
- 一个学生可以加入多个组织
- 一个教师也可以加入多个组织

因此，班级更像“主归属组织”，组织更像“横向协作组织”。

## 成员关系约束

结合你补充的系统规则，推荐在文档中固定以下约束：

### 用户与班级

- 普通用户不能直接视为班级成员
- 学生必须且只能归属于一个班级
- 教师不是班级成员，而是班级关联方

### 用户与组织

- 组织成员只能是学生或教师
- 普通用户不能加入组织
- 学生可加入多个组织
- 教师可加入多个组织

### 教师与班级

- 一个教师可以关联多个班级
- 一个班级可以关联多个教师
- 班级中的教师还可以进一步细分为不同岗位，例如辅导员、班主任、任课老师

## 与当前代码实现的对应关系

当前仓库里已经有部分结构雏形，但还没有完全达到上述目标模型。

### 已有的结构

- `School`
- `College`
- `Classes`
- `Student`
- `Teacher`
- `TeacherClasses`
- `Group`

### 当前已表达的关系

- 学校与学院：已建模
- 班级与教师：已通过多对多关系建模
- 班级与学生：已建模
- 学生与班级：当前是一对一主归属关系
- 班级与群/组织壳：当前通过 `Group` 一对一关联

### 当前尚未完整表达的部分

- `Major` 目前还不是独立实体，当前只是 `Classes.major` 字符串字段
- “组织”目前没有作为独立于班级的成员型组织实体完整建模
- 学生与组织的多对多关系尚未成为显式领域模型
- 教师与组织的多对多关系尚未成为显式领域模型
- “组织成员不能是普通用户”的约束还没有形成统一的数据模型和权限模型

## 对当前 `Group` 的理解

当前代码里的 `Group` 更接近以下两种能力的混合体：

- 班级绑定的会话/群聊载体
- 组织实体的早期占位

但它还不能完全等同于你现在描述的“组织”概念。原因在于：

- 当前 `Group` 与 `Classes` 是一对一关系
- 它更偏向班级群绑定
- 还没有独立的成员关系表去表达“学生和教师可同时加入多个组织”

所以更准确的表述是：

- 当前有 `Group` 雏形
- 未来应拆分出真正的 `Organization` 领域实体

## 推荐的后续领域模型

如果后续要把你描述的结构正式落进代码，建议至少补足这些实体或关系：

- `Major`
- `Organization`
- `OrganizationMember`
- `StudentOrganization`
- `TeacherOrganization`

或者统一设计成：

- `Organization`
- `OrganizationMember`
- `OrganizationType`

再通过 `OrganizationType` 区分：

- `class`
- `departmental`
- `interest`
- `governance`
- `temporary`

如果采用这种统一建模方式，则班级和组织可以共用一套成员框架，但仍保留不同的业务规则。

## 1. 平台账户层角色

这层角色关注“系统级管理权限”，主要用于平台管理和受限命令。

### `user`

- 最基础的账户身份
- 每个绑定到系统的用户都至少具备该身份

### `admin`

- 业务系统内部管理员
- 当前主要由 `User.is_admin` 表达
- 运行时会被追加到 `User.roles`

### `superuser`

- 在 `utils/roles/system.py` 中存在定义
- 当前更偏向运行框架或平台扩展层概念
- 现阶段项目内真正生效的管理员扩展主要通过 `AdminExtension` + `user.is_admin` 判断

## 2. 业务身份层角色

这层角色是项目中最常用的权限入口，定义在 `utils/roles/__init__.py` 的 `UserRole` 中。

### `user`

- 普通用户
- 默认拥有
- 可以进行基础查询、账号绑定、加入组织等通用操作

### `admin`

- 管理员
- 用于受限管理类操作
- 当前典型入口是 `AdminExtension`

### `student`

- 学生身份
- 用户绑定学生实体后自动具备
- 适用于学生侧事务发起、个人资料维护、组织内查询等能力

### `teacher`

- 教师身份
- 用户绑定教师实体后自动具备
- 适用于组织管理、事务治理、审批配置等能力

### `class_cadre`

- 班干部派生身份
- 不是独立账户类型，而是由学生岗位自动派生
- 当 `student.role` 不是普通 `student` 时，会自动附加该角色

## 3. 组织内岗位层角色

这层角色更细，用于表达“在组织中的岗位”，不直接等于命令层权限，但会影响派生角色和业务语义。

### 学生岗位

定义在 `StudentRole` / `StudentRoleLang` 中，当前包括：

- `student`：普通学生
- `monitor`：班长
- `vice_monitor`：副班长
- `secretary`：团支书
- `study`：学习委员
- `life`：生活委员
- `sports`：体育委员
- `organization`：组织委员
- `mental`：心理委员
- `publicity`：宣传委员
- `arts`：文艺委员

说明：

- 除 `student` 外，其余岗位都会让用户额外获得 `class_cadre`
- 当前“班干部”在命令层主要用于请假相关的查看和处理场景

### 教师在班级中的岗位

定义在 `TeacherClassesRole` 中，当前包括：

- `counselor`：辅导员
- `homeroom`：班主任
- `teacher`：任课老师

说明：

- 这是“教师在某个班级中的角色”，不是全局账户身份
- 同一个教师在不同班级中可以有不同岗位
- 当前创建班级时，系统会把创建者默认绑定为该班级的 `counselor`

### 教师身份显示角色

`TeacherRoleLang` 里目前有人类可读的：

- 辅导员
- 班主任
- 任课老师

但当前 `TeacherRole` 存储枚举本身仍比较薄，只保留了较粗粒度的 `teacher`。这意味着：

- 当前全局教师身份是粗粒度的
- 更细的教师岗位主要依赖班级关联关系表达

## 当前角色关系

### 用户与实体关系

- 一个平台账户最终对应一个 `User`
- 一个 `User` 可以绑定多个平台账号
- 一个 `User` 最多绑定一个 `Student`
- 一个 `User` 最多绑定一个 `Teacher`

## 有效角色的计算方式

系统当前真正用于命令筛选的是 `User.roles`，不是单独的 `User.role` 字段。

`User.roles` 的派生逻辑大致如下：

1. 所有用户默认拥有 `user`
2. 如果 `is_admin=True`，追加 `admin`
3. 如果绑定了学生实体，追加 `student`
4. 如果绑定了教师实体，追加 `teacher`
5. 如果学生岗位不是普通学生，追加 `class_cadre`

这意味着：

- `User.role` 更像主身份字段
- `User.roles` 才是运行时权限集合
- 做命令权限、帮助过滤和 AI 能力暴露时，应以 `User.roles` 为准

## 当前命令权限入口

命令层的权限开放主要依赖 `Helper.roles`。

筛选方式在 `Helpers.get_roles_helpers()` 中实现，规则是：

- 如果命令没有声明 `roles`，默认所有用户都可见
- 如果命令声明了 `roles`，则这些角色必须是当前用户有效角色集合的子集

需要特别注意：

- 当前实现是“交集语义”
- 也就是说，`roles={teacher, student}` 表示用户同时拥有 `teacher` 和 `student` 才会被筛出来
- 它不是“教师或学生均可”的并集语义

这意味着当前的权限模型更接近：

- “能力白名单”
- “按有效角色集合过滤”

而不是：

- 单一主身份判断
- 复杂的动态策略引擎

## 当前命令开放示例

以下是根据现有 `__helpers__` 汇总的代表性示例，不是完整权限清单。

这些示例描述的是“帮助系统和 AI 提示层看到的角色声明”，不完全等于最终执行权限；其中多角色声明在当前实现下按交集语义解释。

| 角色 | 典型可用能力 |
| --- | --- |
| 全部用户 | `我的信息`、`绑定用户` |
| `user` | `加入班级` |
| `user` + `teacher` | `添加班级` |
| `student` | `请假`、`提交任务`、`修改学生信息`、`退出班级` |
| `teacher` | `查询班级`、`删除班级`、`设置请假推送` |
| `teacher` + `student` | 在 helper 层声明给同时具备教师与学生身份的用户，例如 `创建任务`、`查询任务`、`删除任务`、`导出任务`、`查找学生`、`at` |
| `student` + `teacher` + `class_cadre` | 在 helper 层声明给同时满足三种角色的用户，例如 `查询请假`、`删除请假` |
| `admin` | `添加学校`、`添加学院` 这类通过 `AdminExtension` 限制的管理能力 |

## 当前实现中的几个关键点

### 1. 班干部是派生角色

`class_cadre` 不是单独创建的账户类型，而是从学生岗位自动推导出来的。

这使得当前系统的角色关系是：

- 学生身份负责“你是不是学生”
- 学生岗位负责“你在班级里担任什么岗位”
- 派生角色负责“你能否进入某些班干部视角的功能”

### 2. 教师身份和教师岗位是两回事

当前系统里至少有两种“教师相关角色”：

- 账户级的 `teacher`
- 班级级的 `TeacherClassesRole`

前者决定是否进入教师侧能力，后者决定在某个班级中承担什么职责。

### 3. 管理员能力当前更偏扩展层

管理员能力目前不是大范围通过 `Helper.roles={UserRole.admin}` 管理，而是有一部分直接通过 `AdminExtension` 做权限拦截。

这说明当前管理员体系已经存在，但还没有完全统一到同一套业务权限模型中。

### 4. 命令层权限不等于领域层权限

当前很多命令先通过 `Helper.roles` 做入口筛选，但真正执行时仍会再检查用户是否具备对应实体或组织关系，例如：

- 是否已经是学生
- 是否已经是教师
- 是否属于某个班级
- 是否是该班级的管理者

因此当前权限链路实际分两层：

1. 命令可见性筛选
2. 业务执行时的实体/组织关系校验

### 5. 多角色命令当前存在交集语义限制

从当前代码看，`Helper.roles` 采用的是子集判断，因此：

- 单角色声明通常符合直觉
- 多角色声明会变成“必须同时拥有这些角色”
- 这与不少命令描述里“教师或学生均可”的直觉语义并不完全一致

因此当前应区分两件事：

- `Helper.roles`：帮助系统和 AI 可见性过滤
- 命令处理函数中的业务校验：真正执行时的限制逻辑

## 当前已知限制

### 1. 教师全局角色表达仍偏粗

当前 `TeacherRole` 本身较薄，无法完整表达全局范围内的教师细分职责。

### 2. 管理员与超级管理员体系尚未完全统一

项目里同时存在：

- `UserRole.admin`
- `system.UserRole.superuser`
- `AdminExtension`

但业务文档和命令层还没有完全统一成一套稳定的治理模型。

### 3. 角色文案层与存储层存在轻微分离

例如教师身份的人类可读角色更细，但存储层当前仍然更粗；这会影响后续做统一权限矩阵时的表达能力。

### 4. 角色体系仍偏“命令权限驱动”

当前系统已经有角色和实体关系，但还没有演进到统一的策略引擎、审批引擎或能力目录层。

### 5. `Helper.roles` 目前不适合表达“或”关系

如果一个能力本意是“教师或学生都可以使用”，当前 `set[UserRole]` + `issubset` 的实现并不能自然表达这一点，后续需要在权限模型中专门收敛。

## 推荐的理解方式

如果从软件设计角度理解当前项目，最合适的方式是：

- `User`：账户主体
- `Student` / `Teacher`：业务身份实体
- `StudentRole` / `TeacherClassesRole`：组织岗位
- `User.roles`：运行时有效权限集合
- `Helper.roles`：命令可见性白名单

这个模型已经能支撑现阶段的班级、请假、任务和组织管理能力，但如果后续要做更复杂的审批治理、校园系统互联、MCP 对外开放和细粒度授权，就需要继续往“领域权限 + 策略治理”方向演进。

## 后续建议

结合当前仓库状态，后续最建议做的不是继续堆更多零散角色，而是按下面顺序收敛：

1. 统一系统管理员、业务管理员和平台扩展管理员的语义
2. 区分“账户身份”“组织岗位”“审批职责”“能力授权”四种概念
3. 让命令层、领域层、MCP 层共用同一套角色与权限目录
4. 将高风险操作从简单角色判断升级为“角色 + 关系 + 审批”联合判定

## 当前结论

当前项目已经具备一个可运行的角色体系，但它是“逐步演进出来的实现型权限模型”，还不是最终的统一授权模型。

现阶段可以把它概括为：

- 普通账户身份由 `User` 提供
- 学生/教师身份由绑定实体提供
- 班干部和班级教师岗位由组织关系提供
- 命令开放由 `Helper.roles` 控制
- 管理能力由 `is_admin` 和扩展层共同限制

这套模型足够支撑当前仓库里的主体功能，也为后续重构成更标准的 `identity and access` / `organization and membership` / `approval and governance` 模型提供了基础。
